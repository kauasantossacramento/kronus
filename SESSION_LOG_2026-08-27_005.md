- [x] `GET /api/v1/colaboradores/`, `/departamentos/`, `/cargos/`, `/escalas/`, `/pontos/`, `/banco-horas/`, `/atestados/`
- [x] `POST /api/v1/pontos/registrar/` — passa pelo **mesmo `RegistroPontoService`** do totem: reserva o NSR, encadeia o hash, dispara a consolidação. Um caminho paralelo quebraria a cadeia e invalidaria o AFD
- [x] `GET /api/v1/pontos/{uuid}/verificar/` — recalcula o hash e devolve o veredito, para uma auditoria externa conferir integridade **sem acesso ao banco**
- [x] `GET /api/v1/banco-horas/resumo/` — agrega o período por colaborador, com `saldo_anterior` e `saldo_final` (a folha precisa dos dois para saber quanto o mês *movimentou*)
- [x] `GET /api/v1/relatorios/afd|aej/` — texto puro ISO-8859-1, **byte a byte igual** ao da tela do RH; teste trava essa igualdade
- [x] `GET /api/v1/relatorios/espelho/` — espelho como dados, não como PDF
- [x] `GET /api/v1/conta/` — identifica a credencial, o plano e a **cota restante**; é o primeiro endpoint que uma integração chama

**Decisões que valem registro:**

- **Nenhum queryset parte de `Model.objects.all()`.** Todos partem de
  `self.empresas()`, o escopo da credencial. Uma chave de Empresa alcança
  uma; uma de Cliente alcança as empresas daquele cliente. Não existe
  terceiro caminho. Sete testes de isolamento cobrem isso.
- **Lookup por UUID, nunca por id sequencial.** Ids incrementais numa API
  pública permitem estimar o tamanho da base e enumerar registros vizinhos.
- **404 idêntico para "não existe" e "existe em outra conta".** Distinguir
  permitiria descobrir UUIDs alheios válidos.
- **`nsr_maior_que` é o caminho recomendado de sincronização.** O NSR é
  sequencial e imutável por empresa; um ajuste retroativo do RH ganha NSR
  novo e por isso não escapa da sincronização — o que paginar por data não
  garantiria.
- **Cancelados aparecem na listagem.** A Portaria anula, não apaga. Omiti-los
  abriria um buraco no NSR e faria a integração suspeitar de adulteração.
- **Desligados ficam de fora por padrão** (`?ativo=false` para incluir): uma
  folha que os recebesse em silêncio pagaria quem já saiu.
- **CID e embedding facial nunca saem.** São dado de saúde (LGPD, Art. 5º, II)
  e dado biométrico (Art. 11); nenhuma integração de folha precisa deles.

### B. Rate limiting, documentação e webhooks
- [x] `apps/api/throttling.py` — `PlanoRateThrottle` resolve a cota **por requisição**, como o menor entre `Plano.rate_limit_api_hora` e `APIKey.rate_limit_hora`. Uma chave não compra cota além do que o plano vendeu, e a troca de plano vale na hora (o `ScopedRateThrottle` padrão leria uma taxa estática do settings)
- [x] `apps/api/schema.py` — extensões `OpenApiAuthenticationExtension`. **Sem isso o Swagger sai sem o botão "Authorize"**: a página abriria e todo endpoint devolveria 401. Documentação que não deixa testar não economiza suporte, gera suporte
- [x] Schema OpenAPI saneado: **de 49 warnings e 4 erros para zero**, com enums nomeados (`ENUM_NAME_OVERRIDES`) — nomes como `Tipo32eEnum` chegariam ao client gerado pelo integrador
- [x] `apps/notificacoes/webhooks.py` — despacho com assinatura **HMAC-SHA256 do timestamp + corpo**. O timestamp entra *dentro* do HMAC: assinar só o corpo permitiria reenviar uma entrega antiga indefinidamente
- [x] `EntregaWebhook` — cada tentativa é persistida, com payload congelado no instante do fato. Retry exponencial (1 min, 5 min, 25 min, 2 h, 10 h); 5 falhas consecutivas desativam o webhook
- [x] `reprocessar_entregas_pendentes` no Celery Beat (a cada 10 min) — rede de segurança: se o broker estava fora do ar no `on_commit`, a entrega continua no banco e é recuperada. Sem ela, um Redis reiniciado perderia eventos em silêncio
- [x] **Nenhuma chamada de rede dentro da transação do ponto.** Todo despacho passa por `transaction.on_commit`, e a chamada é envolvida em `try/except`: um ERP quebrado do cliente não pode impedir alguém de bater ponto. A batida é a obrigação legal; o webhook é conveniência
- [x] Telas do RH: lista, detalhe com **histórico das 50 últimas entregas**, entrega de teste síncrona e reenvio manual. Quando o cliente diz "não recebi", ele mesmo vê o `500` que o servidor dele devolveu
- [x] `apps/rh/signals.py` — `colaborador.criado` / `colaborador.desligado` por sinal (um colaborador nasce de vários caminhos e nenhum é "o" caminho), desligamento detectado por **transição de estado** para não redisparar a cada save

### C. Defeito de conformidade encontrado e corrigido — o achado da sessão

O endpoint de verificação de integridade, recém-criado, reprovou o primeiro
registro do banco de desenvolvimento. `verificar_cadeia` — código da Fase 2,
independente — concordou: `hash_divergente` no NSR 1.

**A causa.** `gerar_hash_registro` serializava `data_hora.isoformat()` como
recebia. O mesmo instante produz strings diferentes conforme o offset:

```
gravação (horário local) : 2026-08-17T08:00:00-03:00  → 832d779a…
leitura  (banco, UTC)    : 2026-08-17T11:00:00+00:00  → db9cf97c…
```

Um único instante, dois hashes. Como os caminhos de gravação — totem e ponto
web — passam horário local e o banco devolve sempre UTC, **o hash gravado e o
recalculado nunca conferiam**. A prova de integridade exigida pela Portaria
671 reprovava registros legítimos: um fiscal que pedisse a verificação
receberia "adulterado" para marcações intactas.

**Por que 441 testes não pegaram.** Todos usam `timezone.now()`, que já é
UTC-aware — escrita e leitura coincidiam. O defeito só aparece com datetime
local, que é justamente o caso de produção.

**Correção.** `gerar_hash_registro` normaliza para UTC antes de serializar. O
hash passa a ser função do *instante*, não da representação do instante.

**Testes de regressão** (confirmados: revertida a correção, os dois falham):
- `test_mesmo_instante_em_fusos_diferentes_da_o_mesmo_hash` — UTC, Brasília e Tóquio produzem o mesmo hash
- `test_instantes_diferentes_dao_hashes_diferentes` — a normalização não achata horários distintos
- `test_cadeia_sobrevive_a_marcacao_gravada_em_horario_local` — integração, pelo service
- `test_verificacao_independe_do_fuso_da_aplicacao` — trocar `TIME_ZONE` não invalida registros gravados

**Reparo dos dados existentes.** `manage.py recalcular_cadeia` — audita e,
sob `--aplicar`, reescreve. O comando classifica cada divergência:

| classificação | significado | ação |
|---|---|---|
| `representacao_de_horario` | confere se recalculado no horário local | é o defeito conhecido, seguro corrigir |
| `divergencia_real` | não confere de nenhuma forma | possível adulteração — **`--aplicar` se recusa a rodar** |

A recusa é deliberada: apagar a evidência de uma possível adulteração junto
com a correção de um bug é exatamente o que não se pode fazer. A operação
grava `LogAcesso.SEGURANCA` e usa `queryset.update()` porque
`RegistroPonto.save()` proíbe alterar o hash — e essa proibição continua
valendo para todo o resto do sistema.

Aplicado ao banco local: **96 divergências de horário, 0 divergências reais,
99 marcações reescritas**. Cadeia verificada em seguida: `integra: True,
registros_verificados: 99`, e 50/50 íntegros pela API.
